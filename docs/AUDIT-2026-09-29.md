# 🔴 CRITICAL

## C1 — Validasi token fail-open: `API_SECRET` kosong → semua token bisa dipalsukan
- [x] Selesai
- **Lokasi:** `gas/Code.gs:191-241` (`generateAuthToken_`, `validateToken_`)
- **Masalah:**
  1. Secret di-fallback ke konstanta hardcoded: `var secret = API_SECRET || 'SIANJAB_DEFAULT_SECRET_KEY';` (muncul di generator **dan** validator). Siapa pun yang membaca kode sumber bisa membuat token admin sendiri: `base64("admin:<timestamp>:<hmac-dengan-secret-default>")`.
  2. Token lama **tanpa signature tetap diterima** selama username-nya ada (cabang `else if (API_SECRET)` hanya menolak jika `API_SECRET` diset; jika kosong, lolos begitu saja).
  3. `handleRequest_` (:325) hanya memvalidasi token **jika** `API_SECRET` truthy — deployment tanpa properti itu sama sekali tidak punya auth.
- **Dampak:** RBAC & seluruh endpoint dapat dilewati; setara tidak ada autentikasi.
- **Perbaikan:**
  1. Fail-closed: di awal `handleRequest_`, jika `API_SECRET` kosong → tolak semua action kecuali `PUBLIC_ACTIONS_` dengan pesan "Server belum dikonfigurasi (API_SECRET)".
  2. Hapus fallback `'SIANJAB_DEFAULT_SECRET_KEY'` dari generator & validator; jika kosong → `throw`.
  3. Tolak token tanpa signature secara mutlak (hapus jalur token lama), atau beri masa transisi 7 hari dengan log peringatan.

## C2 — Backdoor `admin/admin` dibuat ulang terus-menerus
- [x] Selesai
- **Lokasi:** `gas/Code.gs:1369-1427` (`loginUser_`, dua blok identik)
- **Masalah:** Jika username `admin` **tidak ditemukan** (admin dihapus, di-rename, atau dinonaktifkan via `isActive`), login `admin/admin` otomatis **membuat ulang akun admin baru**. Jalur ini hidup di dua cabang (users kosong & users tidak kosong).
- **Dampak:** Jalur masuk permanen yang tidak bisa dimatikan dari aplikasi; cukup ketahui kredensial default lama.
- **Perbaikan:**
  1. Hapus kedua blok dari `loginUser_`.
  2. Ganti dengan fungsi bootstrap manual `bootstrapAdmin_()` yang dijalankan **sekali** dari editor GAS (atau menu admin), hanya saat node `users` benar-benar kosong.
  3. Jika ingin fallback darurat, wajibkan flag di Script Properties (`ALLOW_BOOTSTRAP=true`) yang dinonaktifkan setelah pakai.

## C3 — Secret Firebase ter-commit di file debug di git
- [x] Selesai
- **Lokasi:** `fix_db.js`, `debug_tree.js`, `debug_tree2.js` (semua ter-track git; keduanya memuat URL Realtime Database + `?auth=<DATABASE_SECRET>` yang memberi akses penuh)
- **Masalah:** File skrip one-off berisi kredensial database produksi tersimpan di repositori. Siapa pun dengan akses repo bisa **baca/tulis seluruh database langsung**, melewati aplikasi & RBAC. File `parse_test*.js`, `parse_debug.js`, `patch.js` juga sampah debug yang tidak seharusnya ada di repo.
- **Dampak:** Kompromi database total dari satu file bocor.
- **Perbaikan:**
  1. **Rotasi** database secret di Firebase console (wajib — sudah terlanjur ada di history git).
  2. Hapus semua file debug dari repo (`git rm fix_db.js debug_tree.js debug_tree2.js parse_test*.js parse_debug.js patch.js`); masukkan polanya ke `.gitignore`.
  3. Jika butuh tool serupa, baca kredensial dari environment variable, bukan hardcode.

## C4 — RBAC bocor lewat aksi generik `create`/`update`/`delete`
- [x] Selesai
- **Lokasi:** `gas/Code.gs:174` (`PUBLIC_ACTIONS_` berisi `getSptSpreadsheetData`), `gas/Code.gs:177-184` + `gas/Code.gs:361-371` (switch `handleRequest_`), `deleteRecord_`/`updateRecord_`/`createRecord_`
- **Masalah:** `ADMIN_ONLY_ACTIONS_` melindungi `createUser`/`updateUser`/`deleteUser`, tetapi **aksi generik tidak**. Operator dengan token valid bisa memanggil:
  - `action=delete&entity=users&id=<userId>` → **menghapus user lain** (termasuk admin).
  - `action=update&entity=users&id=X` dengan `{"isActive":false}` atau `{"password":"teks-bebas"}` → menonaktifkan user / menimpa password **tanpa hashing** (mengunci akun).
  - `action=update&entity=settings&id=aiConfig|orgSetting|deadline` → mengubah konfigurasi aplikasi (termasuk mengganti API key AI).
  - `create`/`update`/`delete` pada `jabatan`/`unitKerja` **milik OPD lain** — validasi kepemilikan hanya ada di sisi client.
  - `getSptSpreadsheetData` ada di `PUBLIC_ACTIONS_` → isi spreadsheet SPT terbaca **tanpa token sama sekali**.
- **Dampak:** Operator bisa merusak akun, konfigurasi, dan data OPD lain.
- **Perbaikan:**
  1. Tambahkan guard di `handleRequest_`: untuk `entity === 'users'` atau `entity === 'settings'` pada aksi `create/update/delete` → hanya `admin`.
  2. Untuk entitas ber-scope OPD (`jabatan`, `unitKerja`, `abk`, tabel anjab): jika `currentUser.role !== 'admin'`, baca record target dan tolak bila `unitKerjaId`-nya ≠ `currentUser.unitKerjaId` (untuk `jabatan`, cek `unitKerjaId` record; untuk anak, cek via `jabatanId`).
  3. `getSptSpreadsheetData` dikeluarkan dari `PUBLIC_ACTIONS_` (wajib login), atau diberi token integrasi tersendiri bila memang dipakai sistem eksternal.

## C5 — API key AI provider terekspos ke semua client
- [x] Selesai
- **Lokasi:** `src/lib/api.ts:645-648` (`getAiConfig` membaca `settings/aiConfig` penuh), `gas/Code.gs:2799-2801` (`generateAnjabWithAI_` juga membaca kunci), `src/app/dashboard/pengaturan/page.tsx:87`
- **Masalah:** Kunci Gemini/OpenAI/DeepSeek/Groq/OpenRouter disimpan di `settings/aiConfig` dan dikirim **utuh ke browser** setiap operator/admin (dipakai untuk direct-call dari klien di `api.generateAnjabWithAI`).
- **Dampak:** Kunci berbayar bisa dipakai/berubah oleh siapa pun yang login; tagihan tidak terkendali.
- **Perbaikan:**
  1. Simpan panggilan AI di server (GAS `generateAnjabWithAI_` sudah ada — jadikan satu-satunya jalur; hapus direct-call dari klien di `src/lib/api.ts:683-757`).
  2. Saat `readRecord_`/`readAllRecords_` untuk `settings` dengan role non-admin, strip semua field `*ApiKey`.
  3. Di halaman pengaturan, tampilkan hanya 4 karakter awal + placeholder saat edit.

## C6 — Password SHA-256 tanpa salt + tanpa rate-limit login
- [x] Selesai
- **Lokasi:** `gas/Code.gs:1331-1339` (`hashPassword_`), `gas/Code.gs:1360-1435` (`loginUser_`)
- **Masalah:** (a) Hash SHA-256 polos tanpa salt → rentan rainbow table; (b) tidak ada rate-limit/lockout per IP/username — `writeSecurityLog_` hanya mencatat, tidak memblokir.
- **Dampak:** Brute-force offline (jika DB bocor) dan online (via endpoint login) sama-sama murah.
- **Perbaikan:**
  1. Rate-limit di `loginUser_`: counter gagal per `ip+username` di `CacheService` (maks 5 gagal / 15 menit → tolak + log).
  2. Ganti hash menjadi HMAC-SHA256 dengan `API_SECRET` sebagai kunci server-side (`Utilities.computeHmacSignature(..., password, API_SECRET)`), migrasi bertahap: saat verifikasi, coba format lama → jika cocok, rehash ke format baru.

- **Perbaikan:**
  1. Di cabang edit, kirim hanya field identitas: `{ namaJabatan, kodeJabatan, jenisJabatan, kelasJabatan, parentId, unitKerjaId, urutan }` — **tanpa** `ikhtisarJabatan` dan **tanpa** `level`.
  2. Terapkan di kedua halaman (dashboard & operator).
  3. Tambah guard server di `updateRecord_`: field `ikhtisarJabatan: ''` pada `update` jabatan boleh diabaikan kecuali dikirim eksplisit oleh modul analisis.

## H2 — Fallback ID `temp_` membuat node hantu & orphan permanen
- [x] Selesai
- **Lokasi:** `src/app/dashboard/organisasi/page.tsx:±656-657, 697-698, 725-727` dan `src/app/operator/organisasi/page.tsx:±645-646, 686-687, 714-715` (`handleModalSave`)
- **Masalah:** Jika respons `createJabatan`/`createBatchJabatans` tidak memuat `id`/`items`, client membuat node dengan `id: temp_${Date.now()}` dan menampilkan toast sukses. Node itu tidak pernah ada di database: hilang saat reload, dan jabatan anak yang dibuat di bawahnya memakai `parentId: temp_...` → **orphan permanen** (hanya bisa dibersihkan via `cleanupOrphanedRecords`).
- **Dampak:** Pohon tampak benar di sesi ini, rusak setelah refresh; data anak tersangkut tanpa induk.
- **Perbaikan:**
  1. Hapus fallback `temp_`. Jika respons tidak valid → `throw new Error("Server tidak mengembalikan ID jabatan; cek koneksi lalu muat ulang.")` dan jangan mutasi state lokal.
  2. Sebagai jaring pengaman, jalankan `cleanupOrphanedRecords` otomatis berkala (menu admin) — sudah ada endpoint-nya.

## H3 — Retry otomatis pada operasi tulis → duplikasi record
- [x] Selesai
- **Lokasi:** `src/lib/api.ts:297-330` (`executeActualRequest`, loop `for (attempt < 2)`)
- **Masalah:** Semua request — **termasuk write** — di-retry 1x saat error/timeout. Timeout 30 detik sering terjadi di GAS cold-start padahal Firebase sudah menulis. Retry membuat jabatan/record **ganda**.
- **Dampak:** Duplikasi data susah dilacak, muncul terutama saat server lambat (justru saat rawan).
- **Perbaikan:**
  1. Batasi retry hanya untuk GET (`if (!isWriteOperation && attempt === 0) await sleep(500)`; untuk write, langsung throw).
  2. Alternatif lebih kuat: kirim `requestId` (UUID) pada write; simpan di `CacheService` 5 menit di GAS dan tolak requestId duplikat (idempotency key).

## H4 — Write-queue berisiko eksekusi ganda (struktur then/catch rapuh)
- [x] Selesai
- **Lokasi:** `src/lib/api.ts:437-455` (blok write di `apiCall`)
- **Masalah:** Pola:
  ```ts
  writeQueuePromise = writeQueuePromise.then(async () => { ...eksekusi... })
                                       .catch(async () => { ...eksekusi LAGI... });
  ```
  Eksekusi request ada di **dua cabang**. Saat ini cabang `catch` nyaris tidak pernah jalan (dead code), tapi satu perubahan kecil bisa membuat satu write dieksekusi dua kali — dan tidak ada jalur "lanjutkan antrean setelah gagal" yang benar.
- **Dampak:** Laten/fragile; berpotensi duplikasi tulis atau antrean macet.
- **Perbaikan:** Ganti dengan pola mutex standar:
  ```ts
  const run = () => executeActualRequest<T>(url, true, opts, { action, entity, opts });
  const result = new Promise<T>((resolve, reject) => {
    writeQueuePromise = writeQueuePromise.then(run).then(resolve, reject);
  });
  return result; // antrean tetap berlanjut walau gagal
  ```

## H5 — Invalidation cache bocor untuk aksi tulis dengan `entity: ''`
- [x] Selesai
- **Lokasi:** `src/lib/api.ts:157-196` (`invalidateTargetedCache`), pemanggil: `api.saveABK` (`src/lib/api.ts:600-601`), `api.saveBulkAnjabData` (:758-759)
- **Masalah:** `saveABK`, `saveBulkAnjabData` (dan beberapa aksi lain) memanggil `apiCall(..., '', ...)` → `entity = ''`, sehingga blok `if (entity)` dilewati dan cache hidrasi `entity_<tahun>_abk` (hasil `getBulkData`) **tidak terhapus**. Akibatnya optimistic hydration menampilkan data ABK/anjab basi hingga 3 menit setelah simpan (cache memory + IndexedDB).
- **Dampak:** Pengguna melihat angka lama padahal simpan sukses — tampak seperti "simpan tidak jalan".
- **Perbaikan:**
  1. Di `invalidateTargetedCache`, tambahkan pemetaan aksi → entitas yang terdampak: `saveABK` → `['abk','jabatan']`, `saveBulkAnjabData` → semua entitas anjab, `registerVerificationCode` → `verification_logs`.
  2. Selain itu, putuskan aturan: aksi write **selalu** menghapus `getBulkData` + `entity_*` untuk entitas yang relevan (jangan andalkan `opts.data.jabatanId` saja).

## M3 — Cache GAS gagal senyap untuk data > ±2,7 MB (batas 30 key per `getAll`/`putAll`)
- [x] Selesai
- **Lokasi:** `gas/Code.gs:36-67` (`putLargeCache_`), `gas/Code.gs:70-110` (`getLargeCache_`)
- **Masalah:** Chunk 90KB per key, tetapi `CacheService.getAll/putAll` dibatasi **30 key per panggilan**. Data > ~2,7MB → `putAll` gagal (catch senyap) → setiap request cache-miss → membaca Firebase penuh, kebalikan tujuan cache.
- **Dampak:** Untuk data jabatan kabupaten besar, cache tidak pernah bekerja dan justru menambah overhead serialisasi.
- **Perbaikan:**
  1. Batch `putAll`/`getAll` maksimal 30 key per panggilan (loop).
  2. Turunkan `chunkSize` ke ~50KB dan tambahkan kompresi (`Utilities.gzip` + base64) bila payload besar.
  3. Tambahkan log/metrik hit/miss (properti `DEBUG_CACHE`) agar kegagalan terlihat.
